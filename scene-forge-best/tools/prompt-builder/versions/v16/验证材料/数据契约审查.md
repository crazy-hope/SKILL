# V16 数据契约独立审查

日期：2026-10-30。方式：后端实现者审查未参与实现的前端数据模块；只读代码与运行内存测试，未修改生产代码。

范围：`输出/scene.mjs`、`输出/brief.mjs`、`输出/core.mjs`、`输出/src/workspace.mjs`，并追踪 `src/export.mjs` 和 `src/App.jsx` 的消费路径。依据：本版设计方案、schema5场景结构与后端两阶段接口。

## 发现

### P2：成功历史未强制保留选中构思

位置：[core.mjs](../输出/core.mjs) 第39—44行，`snapshot()` 在验证通用brief后直接返回ready记录。通用brief允许`scene.selected=null`是正确的草稿行为，但成功历史应保留生成时选择，且后端明确拒绝没有选择的最终请求。

复现：构造各项完整的schema5 ready结果，将`brief.scene.selected`改为null。实际调用`snapshot(result)`和`readBackup()`均接受该结果，`resultMarkdown()`仍导出成功双语结果，但完全没有选中构思记录。

影响：损坏或手工编辑的当前版历史/备份会绕过本轮选择的完整性要求，导入和复用时无法追溯生成所依据的关系。正常接口输出不触发此问题。

建议：仅在ready结果快照中要求`brief.scene.selected`非null，保留草稿/预设未选择状态；拒绝无选择的损坏历史，不补造选择。增加snapshot、备份和损坏存储保护用例。

### P2：构思请求期间交付设置变化未使旧响应失效

消费路径：[App.jsx](../输出/src/App.jsx) 第85—103行与第230—248行。`replaceDraft()`对数量与目标模型变化只增加`revision`，不增加`creativeRevision`；`conceive()`却只捕获和检查`creativeRevision`。

因此构思请求发出后切换目标模型或数量，返回的候选仍会写入当前页面。设计方案明确写着“只修改数量或目标模型保留当前构思与选择；其变化仍使进行中的旧请求响应失效”。已有候选可保留与正在返回的旧请求失效是两个独立要求。

建议：构思请求也核对请求修订号；保持现有候选/选择的交付设置例外，另行处理本次正在请求的过期响应与加载状态。若决定允许沿用此类构思响应，应明确修改设计约定，且考虑目标模型硬冲突变化后的行为。

此项来自静态调用链核对，本次未额外启动浏览器交互。
